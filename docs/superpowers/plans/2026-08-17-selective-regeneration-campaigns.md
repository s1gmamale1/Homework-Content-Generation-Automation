# Selective Regeneration Campaigns Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Execution warning:** This is a delivery-program plan, not authorization for one 11-task implementation run. Execute only the delivery unit whose entry gate is satisfied, stop at its PR boundary, and obtain a fresh review before starting the next unit.

**Goal:** Add a separate single-lesson and bulk regeneration feature that creates complete immutable homework revisions from the latest complete version, regenerates selected and affected phases with a versioned repository prompt set, keeps Notion unchanged until explicit publication approval, and produces a durable campaign report.

**Architecture:** A regeneration campaign snapshots its target selection, prompt set, model configuration, phase plan, canary choice, and approvals. Each launched target becomes a normal fleet `HomeworkJob` marked as a regeneration and linked to its source; unchanged phase rows are copied into the new job while selected/affected rows are generated by the existing pipeline, judge, solver, lint, and worker machinery. Publication is a separate approved step that hands successful revision jobs to the durable Notion archive outbox; the old Notion homework remains authoritative until each replacement is confirmed.

**Tech Stack:** Python 3.13+, FastAPI, Pydantic v2, SQLAlchemy 2 async, PostgreSQL/Alembic, existing worker/fenced-lease queue, repository-backed Markdown prompt assets, durable Notion archive outbox, React 19, TypeScript, TanStack Query, pytest/pytest-asyncio, Vitest.

## Global Constraints

- Regeneration is a separate operator feature and API namespace. Do not add a hidden regeneration mode to `POST /jobs/batch`, the Fleet launcher, or the existing `batches` table.
- A single-lesson regeneration is a one-target regeneration campaign and follows the same snapshot, canary, review, publication, reporting, and archival rules as bulk regeneration.
- Every target starts from that `(toc_entry_id, output_language)` pair's latest **complete** homework snapshot. A partial subset job is never a valid base.
- Never mutate, delete, reopen, or attach new usage rows to the source job or its phase rows. A revision is a new self-contained job.
- Unchanged phases are copied into the new job with explicit source-phase provenance. Regenerated phases are absent until the existing pipeline creates them.
- Extraction is copied by default. `refresh_extraction=true` is an advanced, explicit choice and forces every homework content phase into the regenerated set.
- Explicitly selected phases are always regenerated. Their transitive downstream consumers are automatically included by default. Operators may exclude only automatically affected phases, and must acknowledge the inconsistency warning; exclusions are permanently recorded in the campaign and report.
- Prompt text remains repository-owned and code-reviewed. The UI may list/select prompt sets and show read-only metadata, but may not edit prompt bodies in the database.
- `homework-v1` denotes the current legacy prompt tree. This feature does not invent the reshaped prompt content; a later prompt-content commit registers `homework-v2` by adding a complete validated prompt-set directory and manifest.
- Every generation and regeneration job stamps a concrete `prompt_set_id`; every generated phase keeps its resolved prompt hash. Copied phases keep their original hash and point to their source phase.
- Copied phases are not silently re-judged: they retain their original prompt hash, judge/solver verdicts, and warnings. A complete revision may therefore contain old-set copied phases beside new-set regenerated phases; the diff and report must make that mixed provenance explicit.
- Regeneration uses the current campaign-snapshotted launch defaults for provider/model/transport roles, not retired model stamps from the source job.
- The campaign has two human gates: approve bulk generation after canary review, then approve publication after the generation report. No regeneration job may auto-publish on pipeline completion.
- Notion continues to show one live homework per lesson. Publication replaces only the existing HCGA-owned homework for that TOC entry; failed generation or failed archive leaves the old live homework untouched.
- Publication delivery, retry, lease fencing, Notion ownership proof, and dead-letter behavior belong to the durable Notion archive outbox. Do not create a second process-local publisher or `asyncio.Task` registry.
- A publication approval may enqueue only complete revision snapshots. Targets with exclusions or judge infrastructure/major warnings require explicit warning acknowledgement in the publication request.
- Actual campaign cost is calculated only from `agent_usages` attached to revision jobs. Copied phase rows never duplicate usage or spend.
- No production DB write, live Notion request, paid model call, prompt-content rewrite, deployment, or fleet configuration change is authorized by this plan. All integration tests use an isolated scratch PostgreSQL database and fake providers/Notion clients.
- The regeneration API/UI is guarded by `REGENERATION_ENABLED=false` through the core delivery unit. Enabling it in any environment is a separate rollout decision after publication integration passes its acceptance gate.
- Every implementation task follows RED -> verify RED -> minimal GREEN -> focused suite -> review -> commit. Run the mandatory branch-collision gate again before Task 1 and whenever the base or task scope changes.
