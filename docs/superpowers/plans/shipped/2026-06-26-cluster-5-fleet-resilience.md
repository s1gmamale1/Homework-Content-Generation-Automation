## Approach & key decisions

**Scope (the spec's "Design-together note", verified 2026-06-26):** the three campaign-protecting C5 app-code items as **one** workstream — `fleet-net-1` (code half only), `fleet-limited-worker-hogs-1`, `fleet-session-limit-autopause-1`. Excluded: the ops half of net-1 (wired Ethernet / NTP / resolver), `pg-hba-ipv6-1` (DB config), `sse-multipod-1` (separate observability lane), `concurrency-knob-1` Phase 2 token-bucket (**blocked** on Vertex quota numbers). The P1 control plane (pause/drain/reclaim) is already shipped.

**The live failure these fix (grade-8 run, 2026-06-23/24):** a Claude session-limit makes a worker's jobs **fail sub-second at extract**, so the limited worker (Oliver) out-claimed the healthy worker (Mac) and **insta-failed 33 jobs** (English 0/22). Separately, Oliver's transient DNS/connection errors dropped API calls that the 429 backoff doesn't catch.

**Locked decisions (user, 2026-06-26 — in REMEDIATION_CLUSTERS.md):**
- **Limited worker = whole-worker self-cooldown.** A worker that hits a session/rate limit stops claiming **all** jobs until the limit clears, then auto-resumes. The limit is per-account = per-worker, so a healthy peer keeps working. Reuses the shipped self-stop pattern + the `scheduled_at` claim primitive; **no claim-gate surgery**.
- **Session-limit strategy = ship BOTH, operator picks per batch.** `session_limit_strategy` resolved as **per-batch override else `SESSION_LIMIT_STRATEGY` env default**. (a) **pause** — parse the reset time, requeue the job, the limited worker self-cooldowns until reset, auto-resume (batch stays on claude). (b) **switch** — the limited role fails over to a non-limited model and the job keeps moving.
- **Switch reuses the existing failover chain.** On a session-limit under `switch`, classify it as a **`wall`** failure (0 same-provider retries) so `_run_with_failover` immediately advances down `failover_provider_order` (claude→codex→gemini…). A claude job's chain already starts with claude then the fallbacks, so failover **off** claude already works — we only need session-limit → wall so it doesn't burn the wasted "hard" retry, and the pause path to abort instead of switch.

**How `fleet-limited-worker-hogs-1` (stop vacuuming the queue) is fully covered:** the vacuum happened because session-limited jobs **failed sub-second** and the worker kept claiming + insta-failing. Both strategies kill the vacuum: **switch** → the job no longer fails (it completes on the fallback), so there's nothing to vacuum; **pause** → the worker self-cooldowns (stops claiming) until reset, so it can't out-claim a healthy peer. Scope note: the cooldown triggers on the **session-limit** signal (the observed incident, which carries a parseable reset). A generic non-session quota/weekly **wall** (no stated reset) is handled by ordinary failover, not a cooldown — a fixed-duration wall-cooldown is a noted future extension, not MVP.

**Load-bearing facts verified against code (explorer map, 2026-06-26):**
- `agent._spawn` (`agent.py:395-412`) is already a retry-on-transient wrapper; its gate `_is_rate_limited` (`agent.py:354`, terms at `:343`) only matches 429-family terms. fleet-net-1 = widen that gate with connection/DNS terms (auth/MAX_TOKENS stay excluded).
- The session-limit string — **verified verbatim** in `var/server oliver worker.log` (2026-06-23 run): `You've hit your session limit · resets 12:50am (America/Chicago)` — arrives as the claude envelope `result` (`claude.py parse_envelope`) and surfaces in the `RuntimeError` `run_phase` raises (`agent.py:829-832`). The raw envelope also carries `"api_error_status":429`, but the parsed `result` text (what reaches the classifier) is the limit message, so detection keys on that text, not the 429. The current string matches no `_WALL` term (it says "session limit", not "usage limit") so `failure_classifier.classify` returns `"hard"` → 1 wasted same-provider retry then failover. **No reset-parse, no pause exists** (greenfield).
- `_run_with_failover` (`pipeline.py:601-653`) + `_failover_chain` (`:586`) + `_SAME_RETRY_BUDGET={"transient":2,"hard":1,"wall":0}` (`:598`). The requested provider is always chain[0]; claude is excluded only as a *fallback target for others* (isolation), not from its own job's failover.
- `mark_failed_with_retry` (`jobs.py:518-566`) already writes a future `scheduled_at` via `func.make_interval`; `claim_next_job` already honors `scheduled_at <= func.now()` (`jobs.py:388`, DB clock). **`scheduled_at` is the existing "claimable-later" primitive.** Attempts increment at **claim** (`jobs.py:403-415`), not at failure.
- Worker main loop (`worker.py:253-287`) claims → runs → frees its slot → loops back to claim again. The "vacuum" is the **sub-second claim→fail→claim cycle**: a session-limited claude job fails in ~1s, freeing the worker to immediately claim and fail the next, so the limited worker out-claims a slow healthy peer. Slot release is **conditional** (released in `_execute_job`'s `finally` for a claimed job, or directly when `_claim_one` returns None) — *not* unconditional. `_claim_one` (`:334`) is the single claim site to gate on cooldown (skip the claim while cooled down → no vacuum).
- Reuse points: `workers_repo.set_status/get_status`, the self-stop pattern in `_drain_check_and_beat` (`worker.py:598-611`), `batches_repo` for the per-batch column.

**Rejected:** (a) provider-scoped claim-skip for the limited worker — needs per-worker-per-provider claim-gate plumbing; during a single-provider mass-gen the worker idles either way, so whole-worker cooldown is simpler and sufficient (user's pick). (b) Whole-batch pause+scheduled-unpause for the pause strategy — superseded by the per-worker cooldown decision (more correct: the limit is per-account, so a healthy peer should keep draining the batch; we requeue the job *claimable-now* and only cool down the *limited worker*). (c) A stateful "proactive switch" that remembers claude is limited and skips it for later jobs — each later job instead fast-fails one claude attempt then switches (sub-second, no real cost); proactive-skip is a noted future optimization, not MVP.

**Sequencing (one workstream, ordered):** net-1 (small, independent) → classifier+parser (foundation) → strategy column+resolver → failover wiring → worker cooldown+requeue → FE/API per-batch control → finish.

### Task 2 — Classify the Claude session-limit + parse its reset time
- **Files:** `app/services/failure_classifier.py`, `tests/services/test_session_limit_classify_parse.py`.
- **Source the real strings first.** The verbatim captured message (Oliver, 2026-06-23) is `You've hit your session limit · resets 12:50am (America/Chicago)` — confirmed in `var/server oliver worker.log`. Use it (and any sibling variants in that log) as the test fixtures — don't invent the string.
- `parse_session_limit_reset(text, *, now: datetime) -> datetime | None` — regex-extract a `resets <h>[:<mm>]\s*<am|pm>\s*[(<IANA tz>)]` clause (default tz `settings.session_limit_default_tz = "America/Chicago"` when none is stated); compute the **next future** occurrence relative to `now` in that tz (roll to tomorrow if already past), return tz-aware **UTC**. `now` injected (no `datetime.now()` in the parser — testable + clock-discipline). Use `zoneinfo`.
- `is_session_limit(text) -> bool` — **key on the parseable reset clause** (`parse_session_limit_reset(text, now=...) is not None`), NOT a literal phrase. **This is the load-bearing correctness fix (gatekeeper #1):** `failure_classifier._WALL` ALREADY contains `"usage limit reached"`/`"usage limit"` (`failure_classifier.py:33-37`), so a `"usage limit reached · resets 1am"` phrasing would pre-classify as `wall` and the **pause strategy would silently never fire** unless detection (a) keys on the `resets <clock-time>` clause — which catches both the `session limit` and `usage limit reached` phrasings — and (b) is checked **before** `classify` in the failover handler (Task 4). An ordinary wall (weekly/quota, no clock reset) returns False → normal failover.
- **Test:** the verbatim captured string → `is_session_limit True` + parse returns the exact UTC instant for a fixed `now` (cover BOTH "reset already past today → tomorrow" AND "later today"); a `"usage limit reached · resets 1am"` variant → **ALSO `is_session_limit True`** (proves it isn't swallowed by `_WALL`); `"Prompt is too long"` → False / parse None; a `"weekly limit reached"` wall with **no** clock reset → `is_session_limit False`; am/pm + with/without-tz parse variants.

### Task 4 — Wire strategy into phase execution: `switch` fails over, `pause` signals
- **Files:** `app/services/pipeline.py`, `app/services/errors.py` (new, or reuse an existing errors module — a `SessionLimitPause` exception), `tests/services/test_session_limit_strategy_failover.py`.
- New exception `SessionLimitPause(reset_at: datetime | None)`.
- Resolve the strategy **once per job** in `pipeline.run`: load the job's batch (`batches_repo.get(job.batch_id)` if `batch_id` else None) → `resolve_session_limit_strategy(batch.session_limit_strategy if batch else None)`; thread `session_limit_strategy` into `_execute_phase`/`_run_with_failover`.
- In `_run_with_failover` (`pipeline.py:601-653`), in the exception handler: **check `is_session_limit(str(exc))` BEFORE `failure_classifier.classify(exc)`** (this ordering is load-bearing — gatekeeper #1: a `"usage limit reached · resets …"` session-limit matches `_WALL`, so if `classify` ran first the pause strategy would silently never fire). When `is_session_limit`:
  - **switch** → treat as a `"wall"` failure (budget 0 — e.g. branch to the wall path / override the `_SAME_RETRY_BUDGET` lookup to 0 for this exception) so the loop advances to the next provider immediately (no wasted same-provider retry); existing chain logic carries it to codex/gemini.
  - **pause** → `raise SessionLimitPause(parse_session_limit_reset(str(exc), now=...))` — abort the chain (do NOT switch providers), so the worker requeues the job to run on claude after reset. (`now` from a small injected clock helper so it's testable; host clock is acceptable here — the reset is hours out.)
  - Only when **not** `is_session_limit` does the existing `failure_classifier.classify` path run unchanged.
- **Test:** a stub `run_fn` that raises a `RuntimeError` carrying the verbatim session-limit text → with strategy `switch`, the loop advances and returns the fallback provider's result (assert `produced_by` advanced past claude); with strategy `pause`, `_run_with_failover` raises `SessionLimitPause` with the parsed `reset_at`. A non-session-limit error still follows `classify` (regression).
