## R9 — Notion push: markdown tables + code fences render as plain paragraphs (SVG half MOOT)

What remains: **markdown tables and ``` code fences have no branch** in `blocks.py` (verified — zero table/fence handling) and fall through as escaped paragraph text. Deliverable shrinks to (b)+(c) of the original below; (a) SVG-rasterize is dead unless legacy pre-placeholder packets are re-pushed.

- **Issue:** the Phase-1 Notion push writes readable blocks, but an inline `<svg>` diagram (and markdown tables, e.g. teacher-note grids) shows up on the Homework page as raw escaped `<svg…>` / pipe-table text instead of an image/table. ## R11 — Provider failover is not legibly recorded (which model ran a phase, and that it switched)

- **Issue:** after per-phase provider failover (shipped on `Nggaev-v2` 2026-06-04, job-resilience branch), you can tell which provider *finished* a phase but not cleanly that it **switched** or which model actually ran. **Observed live 2026-06-04** (resume+failover smoke, job `6a760767`, history): `case-based-preview`/`flashcards` failed over `opencode → codex → gemini`; the DB shows the end state but not the journey.
- **Root cause (verified in the live data):** three gaps.
  - (a) **`phase_outputs.model_name` goes stale on failover.** `_execute_phase` sets `model_name = phase_model_label` (the *requested* model) at `create_or_reset` time; the new `set_status(provider=produced_by)` corrects `provider` but **not** `model_name`. Live: the gemini-produced rows read `provider=gemini` yet `model_name=opencode/mimo-v2.5-free` — self-contradictory. Refs: `app/services/pipeline.py` `_execute_phase` (create_or_reset model_name + final `set_status`).
  - (b) **A timed-out/cancelled attempt leaves NO `agent_usages` row.** `_run_with_failover` wraps each attempt in `asyncio.wait_for(per_attempt_timeout)`; on timeout it **cancels** `run_phase_prompt` before that call records its usage row. Live: `agent_usages` for the phase shows `codex(f)×2 → gemini(t)` but **no opencode row at all** (the 600s hang is only in the ephemeral server log). Refs: `_run_with_failover` TimeoutError branch (`pipeline.py`), usage recording inside `agent.run_phase_prompt`.
  - (c) **No explicit "failed over" signal.** A switch is only *inferred* by comparing `phase_outputs.provider` ≠ the job's requested provider, or by counting `agent_usages` rows per `phase_output_id`. There is no failover flag/count or ordered provider trail.
- **Deliverable (LOW PRIORITY — failover is rare under the current single-host/claude-default usage; matters for the 24/7 autonomous effort's *observability* pillar, see `docs/PRODUCTION_AUTONOMOUS_GENERATION.md` §5):** (1) on failover success, update `phase_outputs.model_name` to the producing model so provider+model agree (needs `run_phase_prompt` to surface the resolved model, since fallbacks pass `model=None` → provider default); (2) record an `agent_usages` (or dedicated failover-event) row for timed-out/cancelled/failed attempts so the full chain is captured; (3) optionally a structured per-phase trail (e.g. `["opencode:timeout","codex:hard","gemini:ok"]`) or a `failover_count` on `phase_outputs`.

## R16 — Notion subject-page resolution is filename-fragile (Jahon vs O'zbekiston Tarixi)

- **Issue:** for an app-subject split across multiple Notion pages (history → **Jahon tarixi** / **O'zbekiston tarixi**), the correct page is chosen by **substring-matching the keyword against the book filename**. This works for `"jahon"` (book `7-sinf_jahon_tarixi_2022.pdf` resolved to the jahon page, **verified 2026-06-17**), but an O'zbekiston-Tarixi book named **"Tarix Ozb"** would **not** contain `"ozbekiston"` → resolver returns `None` → silent "no Notion page" skip. **Latent** — no O'zb-history book is uploaded yet, so it will bite on the first one.
- **Root cause:** `_resolve_subject_page_id` (`app/services/notion_archive.py:43`) folds the filename `hint` and tests `_fold(keyword) in folded` for each keyword in the dict-form `NOTION_SUBJECT_PAGES` value; the keyword is the literal `"ozbekiston"`/`"jahon"`, so any abbreviated/variant filename misses. Same fragility family as the WISHLIST "Notion anchor auto-resolve" item.
- **Deliverable:** make variant matching robust — (a) require uploaded O'zb-history filenames to contain `"ozbekiston"`, **or** (b) add aliases (`"ozb"`, `"o'zbekiston"`, …) in the mapping / a normalizer, **or** (c) fold into the broader anchor auto-resolve crawl. Guard against loose-match collisions (a too-broad `"ozb"` could mis-match unrelated books).

## R18 — Fleet tray grows monotonically; needs a "Complete" split (blocked on a books-list progress rollup)

- **Issue:** since PR #24 / worklog [[MASTER_MEMORY]] §0071 removed the `!fullyBatched` exclusion (which was wrongly making launched books vanish), the Fleet "to launch" tray now keeps **every** prepared book forever — launched and fully-complete books never leave it. Fine for a handful of books; for the Oct/Mar all-subject campaign ([[oct-mar-content-campaign]], potentially hundreds of books) the tray becomes an unwieldy wall.
- **Root cause / why deferred:** an honest "Complete" section (or collapse-done) can't be built at the **group/tray** level today — `GET /api/v1/books` returns `toc: null`, so the tray only knows a book's *batches*, not its per-lesson done counts. Per-lesson truth currently lives only inside each card's lazy `getBook` fetch (`launcher.tsx` `ReadyCard`). A batch-level "complete" split would re-introduce the over-claim bug 0071 just killed (batch-complete ≠ all lessons done — a partial launch reads as complete).
- **Deliverable:** add a **books-list per-lesson progress rollup** (backend: include `lessons_total` + `lessons_done` per book on `GET /books`, or a dedicated `/books/progress` endpoint), then split/collapse the Fleet tray so completed books move to a "Complete" section (or fold away), keeping "to launch" scoped to ready + in-progress. A client-side per-book `getBook` fan-out is a possible FE-only stopgap but is N-queries; the backend rollup is the clean shape. Pre-campaign nice-to-have, not blocking current scale.
- **Also blocked here — `monitor-card-clarity-1` item 2(b) (the accurate combined total):** the monitor batch card now shows an honest per-transport note (`done 18 CLI · 13 API`, worklog 0093, item 2a) but deliberately does NOT show a combined book total, because a naive sum over-counts when the same lesson is done on both CLI and API (real overlap, proven on book `62865c70`: cli_done 1 + api_done 2 = 3 > 2 distinct). The accurate version — `X/31` = **distinct** lessons done on *any* transport — needs the same backend book-level per-lesson **dedup** rollup as the Fleet-tray split above. Ship both off one endpoint.

## R23 — Launched jobs are permanently pinned to their launch-time role models ("resume with current defaults")

- **Issue:** changing `/settings` launch-defaults (or fixing a bad model pick) has no effect on already-created jobs — batch resume/retry replays the exact stamped spec forever. **Observed live 2026-07-14 twice in one afternoon:** job `f45121a7` was stamped `extract_model=gpt-5.3-codex-spark` (128k context — can't hold a whole book); the operator fixed `/settings` to `gpt-5.4`, retried, and it failed identically because retry replays the stamp — required a manual SQL patch of the job row. Same family as the worklog-0133 batch_id resume gap. Operator-annoying at fleet scale: a bad default stamped onto a 60-job batch means 60 permanently-poisoned rows.
- **Root cause:** per-job pinning is **deliberate** (self-describing jobs, honest `agent_usages` attribution, retry-can't-morph — see [[per-job-selection-overrides-env]] / [[flow-games-roles-retry]]): `pipeline._resolve_extract` etc. read `job.<role>_model or ld.<role>_model`, so a non-NULL stamp always wins; the batch-launch resume path re-enqueues failed/cancelled jobs without touching their stamped role fields. There is simply no re-stamp affordance — the only levers are fresh launch or hand-SQL.
- **Deliverable:** an explicit opt-in **"resume with current defaults"** on batch relaunch (API flag + FE toggle) that, for the failed/cancelled jobs it re-enqueues, re-stamps the role fields (`extract_/judge_/solver_ provider+model+transport`, and content `model` within the same content provider) from the current launch-defaults/launch payload. Constraints: content **transport** stays fixed (batch identity is `UNIQUE(book_id, transport)` — a transport change correctly forks a new batch); done jobs untouched; re-stamped values must pass the same `is_valid`/`validate_transport`/self-grade checks as a fresh launch (resolve-then-validate — don't let a stale default bypass `is_valid`, the trap noted in the 0135 investigation). Default OFF so plain retry keeps exact-spec semantics.

## R24 — Long fact-dense lessons produce packets that cover the material but don't teach it (fixed drill budget)

> Filed straight to ROADMAP (worked-up on arrival — issue, root cause and evidence all established before filing); the WISHLIST line is a pointer, not a prior entry.

> **Evidence is durable and re-runnable:** `docs/research/2026-07-20-teaching-audit-drill-density.py` (deterministic, no model calls, $0) + its 1,362-packet dataset `docs/research/2026-07-20-teaching-audit-drill-density-data.json`. The teaching-audit side is `app/services/teaching_audit.py` (worklog 0148/0152).

- **Issue:** on long lessons (7+ printed pages) the generated packet **covers** the lesson yet a student studying only that packet learns little of it. Measured with the teaching audit (worklog 0148): long history lessons scored **10/31 objectives learned (32%)**, versus **14/18 (78%)** for SHORT history lessons drawn from the *same books, grades and authors* — span was the only variable. Worst case is reproducible, not noise: G8 "Muhammad Xorazmshohning mamlakat mudofaasiga oid tadbirlari" (15pp) audited **3 independent times → 0 of 17 objectives learned (0%)**, with essentially every objective marked `coverage=taught`. This class is **structurally invisible to the LLM judge**, which grades a packet against its own prompt/extract and therefore cannot see that the packet under-teaches its source lesson.
- **Root cause (measured, not inferred):** the flow is a **fixed 11-phase set regardless of lesson size** (`flows.flow_for` — `_BASE_PHASES` + `_GAMES` + boss-arena + reflection), so the drill budget does not scale with factual load. Across 1,362 done `uz` packets: drill items are ~flat — **202.4 (short 0-3pp) → 205.0 (mid) → 209.6 (long 7+pp), +3.6%** — while discrete facts nearly double, **25.2 → 44.2 → 48.2**. Median **items-per-fact drops 39% and then saturates: 9.14 → 5.56 → 5.56** — beyond ~4pp, extra lesson length buys a student no extra practice at all. Long history is the extreme: **81.6 facts, 2.57 items/fact** (n=50), against biology 5.65 (n=7), geometry 8.83 (n=23), chemistry 11.74 (n=12), algebra 17.93 (n=17). *(Figures corrected at gate review — the first script version silently excluded 2 of 9 drill phases via wrong `_GAMES` names, understating every item count by ~13%; the conclusion was unchanged.)* Two methodologically independent lines — a simulated-student exam and a deterministic markdown count — agree.
- **Deliverable (fix shape NOT yet chosen — decide at the plan gate):** long fact-dense lessons reach learnability parity with short ones, proven by re-auditing the same packets. Three candidate shapes, materially different, and the current evidence does **not** discriminate between them:
  1. **Scale drill volume to factual load** — the literal reading. Caution: ~9 items/fact × 82 facts ≈ 750 items is an unusable packet, so this cannot be applied naively. The corrected figures weaken this shape further: long packets **already carry ~210 drill items**, so the problem is unlikely to be that they are too small.
  2. **Prioritise instead of expand** — keep the budget, drill the *core* the lesson's objectives target rather than spreading thin across every fact. Possibly *less* content, better chosen.
  3. **Chunk long lessons** — split a 15pp lesson into multiple packets so each gets a full budget. Touches launch/TOC semantics, not just prompts.
- **Open question for the gate (product, not engineering):** the audit's contract is *"a student with only prior-grade knowledge, given nothing but the packet, passes an exam derived from the textbook lesson"* (user-set, 2026-07-17). Homework normally **supplements** a taught lesson, so for a 15pp narrative lesson that bar may be stricter than the product needs. If the intended bar is "reinforces the core the teacher covered", long history is less broken than 32% suggests and shape (2) becomes the obvious answer. **Reaffirm or adjust the contract before choosing a shape.**
- **Known limits of the evidence:** the "facts" proxy counts years + numbers + proper nouns, which *inherently* favours history and under-counts method-based subjects — so the length trend is solid but the **subject ranking is softer than the table implies**. Literature (`adabiyot`), the other genuinely fact-dense subject, has too few done jobs to appear (n<3) and was never audited. Audit-side sampling was 6 history books; the deterministic side covers the whole corpus. ~$5.40 of audit spend produced this; further measurement is not expected to change the picture — the remaining ambiguity is a design decision, not a data gap.
