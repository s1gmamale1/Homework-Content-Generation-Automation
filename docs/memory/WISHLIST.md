- `cancel-race-1`: **A cancel signal gets clobbered → a single `cancelling` write rarely sticks; cancelling an in-flight job is unreliable.** `jobs.set_status` (`jobs.py`) assigns `job.status = status` with **no terminal/cancelling guard**, and the pipeline rewrites `status='running'` on **every phase transition** (`pipeline.py:676`, `current_phase=phase_name`). The worker's heartbeat only samples for `cancelling` every `settings.heartbeat_seconds` (~30s, `worker.py:321`). So a one-shot `running → cancelling` (the `request_cancel` path) is overwritten back to `running` by the next phase-start before the heartbeat can catch it → the CLIs keep running. **Observed live 2026-06-18:** cancelling the math-algebra g9 api batch (`9366822e`), 4 in-flight jobs on worker `Oliver` bounced `cancelling → running`; had to **re-assert `cancelling` continuously for one full heartbeat cycle** until the heartbeat sampled it and tore the tasks down (all 4 settled in ~16s). (`pending → cancelled` via `cancel_if_pending` is fine — it's atomic and the row can't have been claimed; the race is only on RUNNING jobs.) **Fix:** guard `set_status` so a `cancelling`/terminal status can't be overwritten by a `running` write (e.g. `WHERE status NOT IN ('cancelling','cancelled','done','failed')`), OR have the heartbeat treat any non-`running`/`pending` status as cancel, OR shorten the cancel-poll interval. Ties to `cancel-1` (cancel follow-ons) and blocks a future `fleet-ctrl-1` batch cancel-all (a loop of `request_cancel` would hit this same race). Verified live 2026-06-18.
- `concurrency-knob-1`: **The live LLM-concurrency cap reads the *deprecated* setting; the "real" knob is dead — and the semaphore is per-process, not deployment-wide.** `agent.py:203` builds the one process-wide CLI semaphore as `asyncio.Semaphore(settings.gemini_max_concurrency)`. But `config.py:62-63` comments `agent_max_concurrency` as the live "process-wide cap on concurrent CLI subprocesses" and marks `gemini_max_concurrency` **DEPRECATED** — exactly backwards from what the code reads. `agent_max_concurrency` has **zero readers** (grep-confirmed), so setting `AGENT_MAX_CONCURRENCY=N` does NOTHING; the only knob that works is the "deprecated" `GEMINI_MAX_CONCURRENCY`. Both default to 8 so default behavior is identical — which is why it went unnoticed (Wave 3E renamed the setting but never switched the semaphore). Worse, the semaphore is a **module global → per-process**, so the "deployment-wide cap" framing is false: with N worker processes the real fleet cap is N×8, and there is **no 429/`Retry-After` backoff** → a Vertex over-quota event mass-fails instead of throttling. **Fix:** (a) switch `agent.py:203` to read `agent_max_concurrency` (and delete/alias the old name) so the doc/intent matches code; (b) for true fleet control, a shared token-bucket per `(provider, model)` (e.g. DB/Redis) + Retry-After-aware backoff. DEPLOY.md de-staled accordingly 2026-06-18 (the doc had inherited the inverted comment). Verified live 2026-06-18.
